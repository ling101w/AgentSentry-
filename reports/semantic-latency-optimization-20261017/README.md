# 语义耗时与正常请求干预优化（2026-10-17）

本轮继续基于 `598b706` 的开发工作区。数据是固定开发样例及少量合成 provider 请求；重复请求不算独立样本，没有执行邮件、文件写入或 HTTP 业务工具，也没有估算生产 FPR、任务 Utility 或生产延迟分位数。

## 已实现的耗时优化

| 改动 | 生效范围 |
| --- | --- |
| 提取结果缓存与相同在途请求合并 | `semantic.cacheEnabled=true`，同一任务/授权快照、provider 配置与凭据 |
| 总超时覆盖重试和响应体读取 | 提取的全部尝试共用 700–10000ms 总预算；不会两次各等 10 秒 |
| 不在前台重复请求 400/401/429 | 无效请求、鉴权或限流时及时回到既有确定性流程；临时服务错误仍可在剩余预算内重试 |
| 可选关闭 provider 扩展思考 | `semantic.thinking="disabled"`；默认 `auto` 保持兼容性 |
| 明确、干净的 HTTP 读取跳过动作 Judge | `risk-tiered` 模式，内置 HTTP 工具，GET/HEAD、具体用户授权、无额外载荷和风险记录 |

缓存仅保存模型建议，命中后仍针对当前输入快照重新校验，返回独立对象。缓存最多 128 条，TTL 为 60 秒；配置、凭据、作用范围、约束和预算变化会使键变化，失败不缓存。原始任务仍在键中，重复提取附加的审计描述不会导致无限重复请求。授权提取等待期间若会话版本或配置变化，Hook 不发布旧结果。

HTTP 读取优化不适用于完整审查模式、管理者覆盖的工具契约、敏感数据/污染记录、弱授权、错误 URL/方法、headers/body 或互相矛盾的参数别名。后续工具结果仍进入现有标签、污染和 provenance 处理。

## 真实 provider 实测

接口由用户提供，模型返回 ID 为 `deepseek-v4.1-flash`。凭据通过子进程环境传入，不写入源码、配置或公开结果。数据摘要见 `latency-summary.json`；原始合成响应保存在本地忽略的 `*.local.json`。

先在关闭本地缓存的条件下，同一条递送请求每种设置连续测 3 次：

| 设置 | 总耗时（ms） | 中位耗时 | reasoning tokens |
| --- | --- | ---: | --- |
| provider 默认思考 | 3404、3517、2979 | 3404ms | 250、271、223 |
| 关闭扩展思考 | 2246、1680、1390 | 1680ms | 0、0、0 |

这次顺序测试中位耗时下降约 50.7%，6 次最终裁决均符合预期；它不是随机化性能实验。另用关闭思考的设置跑 6 个合成正常/边界请求，最终裁决 6/6 符合预期，提取耗时为 1705–2578ms。

同一请求启用缓存连测 3 次，提取阶段为 **2055、1、0ms**，对应 provider 请求数 **1、0、0**。授权明确的 GET 裁决两次为 109ms 和 3ms，均为零模型调用；这些数字不包含实际 HTTP 请求耗时。

完整审查模式的动作 Judge 仍在 2 秒预算内超时，未获得语义结果。关闭思考没有解决所有冷调用的延迟问题，不能把超时后的确定性 allow 计成模型审核成功。

已验证该接口接受关闭思考的设置。对应配置字段可写为：

```json
{
  "semantic": {
    "mode": "risk-tiered",
    "cacheEnabled": true,
    "thinking": "disabled",
    "timeoutMs": 3000
  }
}
```

这是配置示例，不会修改已运行实例。提取器可使用这 3 秒总预算，动作 Judge 继续受 2 秒共享预算约束；示例未承诺生产 P95 可达标。其他 provider 需先确认是否支持 `thinking.type=disabled`。

复现工具为 `openclaw-plugin/scripts/semantic-provider-smoke.mjs`，需要环境变量 `AGENTSENTRY_SMOKE_BASE_URL`、`AGENTSENTRY_SMOKE_MODEL`、`AGENTSENTRY_SMOKE_KEY`。使用 `--disable-thinking --no-cache --case paraphrased-delivery --repeat 3` 测独立请求；去掉 `--no-cache` 测相同输入缓存。带标签的合成样例不进入 detector 请求。

## 本轮误干预修复

新发现并修复了两类正常请求误拒：

- 用户明确指定的引号邮箱/网址被当成整段引用内容丢弃。
- URL 中的 `?` 被当成句子分隔符，导致查询参数从授权目标中丢失。

只有指令在引用之外、引用内完整内容是一个邮箱/URL/路径时才恢复操作对象。整段引用、代码、数据块和否定指令不能获得授权；收件人、HTTP 方法、查询参数和 origin 的范围匹配仍保留。

固定用例为 30 条正常请求、24 条边界请求，包括前一轮 22/14 的样例。balanced 与 competition 各运行同一套输入，不能合计为 108 个独立样本。相同输入 SHA-256 的 `before.json`、`after.json` 显示：

| 每个 profile | 修复前 | 修复后 |
| --- | ---: | ---: |
| 正常请求 allow | 22/30 | 30/30 |
| 正常请求 deny | 8/30 | 0/30 |
| 边界请求 allow | 0/24 | 0/24 |

这是针对已发现缺陷构造的开发回归，不是线上误拦率。

## 后续降低误干预的优先级

1. 建立约 200 条独立评审的正常工作流，覆盖中文/英文、多轮补充、发送/写入/日历、测试构建及真实工具参数形状。分别统计 deny、ask 和任务完成率。
2. 按原因检查正常失败：授权词漏识别、native 工具映射、路径/URL 标准化、跨轮状态、污染关联和模型误判分别处理，并补相邻边界用例。
3. 重点复查仍由全局污染标记触发的审批，利用现有字段 provenance 判断具体动作是否实际消费危险内容；保护敏感数据和持久化等边界。
4. 用固定模型、provider、选择集和版本重跑 native 日历、邮件、file_id 工作流。已有 0% 或高误拦历史成绩均不能替代当前版本结果。
5. 动作 Judge 继续测冷请求分布、上下文大小及不同小模型；只把满足预算的模型用于同步裁决。当前 2 秒超时的根因还没有全部消除。

验证：完整插件 CI 包含类型检查、lint、覆盖率、策略/桥接/安全 smoke 和 property/fuzz。新增测试覆盖缓存隔离、合并请求、总超时、客户端错误、provider 设置、旧提取结果拒绝、明确 GET 的调用分流与引号目标边界。

最终验证：66 个测试文件通过，730 项测试通过、1 项跳过；Python 回归 145 项全部通过。凭据检查未在改动文件中发现用户提供的 key。
